  `AnesthesiaRecord.agents_used`, `TeleReport.findings`.

  ciphertext (broke reads right after `.create()`, e.g. `FHIRImagingService`).
  Now returns the ciphertext for Django to persist and leaves the instance in
  plaintext. Re-saving a value read masked raises instead of blanking the column.

  from Windows-default-codec batch writes; swapped for ASCII hyphen.

- **3 "order-dependent" cyidentity integration failures**: root-caused,
  not just patched around. `unittest.mock.patch.object(django.conf.
  settings, "KEYCLOAK_ENABLED", False, create=True)` — used ~20 places
  across `cyidentity` + `tenant` tests — silently and *permanently*
  deletes `KEYCLOAK_ENABLED` from Django's settings for the rest of the
  test process once used. Mechanism: mock's `get_original()` can't find
  the attribute in `LazySettings.__dict__` (it lives on
  `settings._wrapped`), so `local=False`; on `__exit__`, mock's own
  source has a documented special case ("needed for proxy objects like
  django settings") that re-`setattr`s the original value in exactly
  this situation — but only when `self.create` is falsy. `create=True`
  suppresses that restore, so `__exit__` calls `delattr` and it sticks.
  Once gone, every later `getattr(settings, "KEYCLOAK_ENABLED", True)`
  falls back to the real-Keycloak default, so any later integration test
  that doesn't itself patch the setting makes a real network call and
  times out — exactly the "depends on run order" symptom, and exactly
  matching a comment already sitting in `test_integration.py` calling it
  "pre-existing, documented flakiness, not introduced here." Fix: drop
  `create=True` from all ~20 occurrences (the setting always exists in
  `core.settings`, so it was never needed). Rewrote that stale comment to
  record the actual mechanism instead of shrugging at it.

## 28. RLS staging enforcement — closed for real, 4 bugs found (session tail 18)

The last "blocked, needs infra" item. Docker Desktop turned out to be
available in this sandbox, so ran the actual thing instead of leaving it
blocked: a real PostgreSQL 16 container, a genuine non-superuser/
non-BYPASSRLS app role, `migrate` → `apply_rls` → `verify_rls` — the exact
runbook `apply_rls`/`verify_rls`'s own docstrings describe, not a
simulation. Nobody had apparently ever run this against live Postgres
before — 4 real bugs surfaced on the first attempt:

1. **`rls_ddl.py` (production code, the serious one)** — the RLS policy
   itself crashed instead of failing closed. `current_setting(guc,
   true)::uuid` raises a hard error when the GUC is `''`, and
   `clear_tenant_guc()` (called by `TenantContextMiddleware` after *every*
   tenant-scoped request) sets it to `''` rather than unsetting it. On a
   pooled connection, any platform-admin (`tenant_id=None`) request reusing
   that connection would 500 on every single RLS-protected query — a real
   production bug, not a test artifact. Fixed with `NULLIF(current_setting
   (guc, true), '')::uuid`.
2. **`verify_rls.py`** — the text-probe literal was inserted unquoted into
   raw SQL, so any NOT-NULL varchar/text column broke the whole command
   before it could check anything.
3. **`verify_rls.py`** — probe columns were computed once and shared
   between both tenants' rows, so a NOT-NULL UNIQUE column collided between
   the two inserts. Now generates fresh values per row.
4. **`verify_rls.py`** — the probe literal didn't respect
   `character_maximum_length`, so a `varchar(<14)` column crashed with an
   unhandled traceback. Truncates to fit now; wrapped the probe block so
   any other unforeseen constraint violation becomes a clean `CommandError`
   instead of a leaked traceback.

with no `@pytest.mark.django_db` — hard-errors for a different reason when
actually run against Postgres); self-skips there now, matching
