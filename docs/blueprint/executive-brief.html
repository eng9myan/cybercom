A

Strategy — build the core once, express every industry as a flavor

Why consolidate. CyShop is ~90% duplicate of CyCom and does not sit on the shared core — pure maintenance cost. CyMed already proves the model: 16 healthcare apps on the same platform/ without duplicating identity, tenancy, or provisioning. Retail should be a flavor the same way healthcare is.

Why it's the moat. The differentiator is cross-domain, not any single module. A clinic that runs its retail pharmacy, its branded shop, its procurement, its payroll and its patient billing on one tenant, one ledger, one identity is something Odoo, Foodics and the SAP/Oracle mid-market cannot do without heavy integration work.

Why once. ZATCA Phase 2, PDPL residency, GOSI/gratuity payroll, WPS, Arabic/RTL — each built once in the core and inherited by every flavor. Three products means three times the compliance surface and audit cost.

What we're not doing. Not a big-bang rewrite — CyCom's core is the foundation. Not microservices-first — a modular monolith with five deliberate carve-outs. Not chasing Odoo on breadth — winning the Gulf multi-domain operator no incumbent serves well.

The one line Build the core and the compliance once, express every industry as a flavor, win the Gulf multi-domain operator, and never let the three-product split come back.

How it becomes the go-to system for any business

Not by hand-building 50 products. Four mechanisms, used in this order: 1 · Configuration — toggle core modules, set presets (AI-propose at onboarding).   2 · Flavor packs — versioned config + attribute profiles + layouts + KPI + regulatory packs; product team + certified partners; no deploy.   3 · Flavor Studio — a visual builder for custom objects, fields, workflows, screens, reports, APIs — tenant-scoped, metadata only, the Odoo-Studio / Salesforce-platform play.   4 · Extension apps — sandboxed code for genuinely novel logic, installed per tenant. Every vertical decomposes into ~10 canonical primitives (Party · Item · Agreement · Transaction · Location · Resource · Schedule · Document · Ledger · Rule); a factory, a utility, a ministry or a university each reuses 60–80% of the core and adds 3–5 first-class nouns. The finite list of ~25 such [core+] primitives is the real "build once" work, spread across the rollout. Full treatment: docs/blueprint/N.

Data model & the 3 → 1 migration

One canonical model. Flavor-specific fields live in registered attributes profiles or CDAC-reviewed extension tables — never a forked model. ~30 core entities: Tenant · Organization · Branch · User · Membership · Role · Policy · Catalog · Product · Variant · SKU · PriceList · Order · Fulfilment · Payment · Invoice · InventoryLocation · StockItem · StockMove · Customer · Vendor · PurchaseOrder · LedgerAccount · JournalEntry · TaxRule · Employee · PayrollBatch · Payslip · Appointment · VerticalFlavor · Integration · ConsentGrant. Health adds Patient · Encounter · ClinicalOrder · Claim as typed extensions.

Core APIs

POST /onboarding/tenants POST /catalog/{id}/products POST /orders · /orders/{id}/checkout POST /inventory/sync POST /scheduling/appointments POST /payroll/batches/{id}/run

REST for commands (OpenAPI 3.1), GraphQL for read/aggregation, signed webhooks + an AsyncAPI event stream for push. URL-major versioning, two majors concurrent, 6-month deprecation window. A self-serve developer portal with sandbox tenants.

F

Governance & Gulf compliance

Cross-Domain Architecture Council (CDAC) owns the canonical data model, API contracts, event schemas and flavor standards so the three-product split never returns. Weekly review; RFC + ADR process; CODEOWNERS on platform/ and core models. Every new flavor passes a "thin flavor" checklist as a hard release gate — no new top-level model, no bespoke frontend, tax handled by presets not code branches.
